# Phase 3: Fine-tune via LLaMA Board

Course equivalent: **"Fine-tune model via LLaMA Board"** (`GRADIO_SHARE=1 llamafactory-cli webui`, then
configure the Train tab by hand).

## How the run was launched

LLaMA Board was started locally (`GRADIO_SERVER_PORT=7860 llamafactory-cli webui` from the
`LLaMA-Factory/` folder). It was then driven in a real (headless Chromium) browser by
[`scripts/llamaboard_train.py`](../scripts/llamaboard_train.py) (Playwright). The script performs the
course's manual clicks, so the run is reproducible and recorded on video for the demo:

and writes everything into its **Output Dir**:
`LLaMA-Factory/saves/Qwen3-1.7B-Base/lora/train_2026-11-08-22-39-50`. That path is the
course's `ADAPTER_DIR`.

## Result

| | |
|---|---|
| Status | **Finished**: 90 / 90 optimizer steps, 3 epochs |
| Runtime | 4,137 s ≈ **69 min** on the Apple M2 GPU (`mps`) |
| Loss | **7.16** (step 5) → 0.29 (end of epoch 1) → **0.19** (step 90); mean over the run 0.88 |
| Tokens seen | 155,200 (468 tickets × 3 epochs) |
| Adapter | [`adapters/qwen3-1.7b-support-router-lora/`](../adapters/qwen3-1.7b-support-router-lora/): `adapter_model.safetensors` (35 MB, rank 8 on q/k/v/o/gate/up/down) |
| Saved with it | tokenizer + **`chat_template.jinja`** (LLaMA-Factory replaced the Qwen template with the `default` training format), `trainer_log.jsonl`, LLaMA Board's own `training_loss.png` |

The adapter's `chat_template.jinja` was checked: it renders
`System: …<|endoftext|>\nHuman: …<|endoftext|>\nAssistant:`, exactly the prompt the model was
trained on. That's why inference (Phase 5) loads the tokenizer **from the adapter folder**.

### Step time

| Steps | Avg. s / step | What was happening on the Mac |
|---|---|---|
| 1–30 | ~53 | headless Chromium was recording LLaMA Board to video (≈180 % CPU + ffmpeg), iCloud Drive syncing the project folder |
| 30–55 | ~55 | browser closed at step 30, but no speed-up yet (iCloud sync, ~2 GB swap in use) |
| 55–90 | ~33 | system load settled |

The 3-step smoke test before the run had measured ~21 s / step on an idle machine. So for
training on a 16 GB laptop: **close everything else, and keep the project out of a
cloud-synced folder.** Stopping the browser automation didn't affect training. LLaMA Board runs
the trainer as its own subprocess and only stops it on **Abort**. When the page was opened
again afterwards, LLaMA Board showed *Finished.*
([screenshot](../results/phase3_llamaboard/08_llamaboard_finished_toast.png)), and the logs are in
[`results/phase3_training_logs/`](../results/phase3_training_logs/).

### First look in LLaMA Board's Chat tab

The Chat tab loaded `Qwen3-1.7B-Base` + the adapter (template `default`, temperature 0.01). Three
tickets in the training format were sent:

| Ticket | Course expects | Model answered |
|---|---|---|
| Please create a new user account for the new employee starting Monday. | Active Directory | **Support general** |
| Outlook keeps asking me to re-enter my password and Teams won't sync. | O365 | **O365** ✅ |
| We're ready to retire [SERVER] — please remove it from monitoring. | EOL | **EOL** ✅ |

The model answers with a bare label, as trained. The "new user account" miss is explained by
the data, not by the training: in `train_split.csv` the tickets asking for a *new user account* are
labelled **Fileservice 9×, Support general 3×, Active Directory 2×**. The model learned the
dataset's (noisy) convention. Phase 5's smoke test and Phase 6's evaluation look at this in detail.
